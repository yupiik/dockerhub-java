=== Automated JRE releases

The standalone Maven project in `_internal` uses Yupiik Fusion CLI, JSON and HTTP client modules.
See link:_internal/README.adoc[the three-step getting started guide] and the link:_internal/src/main/minisite/content/index.adoc[operator minisite sources] for the release flow, contextual token setup and permissions.
Build the browsable documentation with `mvn -f _internal/pom.xml -Pminisite package` and serve `_internal/target/minisite`.
It requires a host JDK 21 or later; the published runtimes start at Java 17.
It discovers ordinary GA, community-available musl *JRE* archives for AMD64 and ARM64 from Azul and stable Alpine tags from Docker Hub.
JDK, JavaFX, CRaC, early-access and glibc distributions are excluded.
All catalog pages are read, numeric versions are compared numerically, and HTTP errors abort discovery rather than treating an unavailable catalog as empty.
HTTP requests use Fusion's curl logger without response payloads, with sensitive headers masked and a configurable one-minute default timeout.
The public catalog requests do not need credentials.

Only the latest Java patch/build *per Java major >=17* is paired with the latest stable Alpine release supporting both architectures.
There is no intermediate-patch backfill and no Java-patch by Alpine-patch cross-product.
For example, if Java 21.0.2 and Alpine 3.20.0 are latest, discovery queues only `21.0.2-alpine3.20.0`, not every intervening 21.0.1/21.0.2 and 3.19.x/3.20.x combination.
If the newest Java release/build is not available on both architectures, that major is deferred rather than falling back to an older patch.
All available majors, including upstream end-of-life majors, are considered; discovery is not a promise of ongoing upstream security support.
Legacy floating tags such as `21.0.1-alpine3` cannot identify an exact Alpine patch and do not suppress a new fully versioned release.
A numerically newer existing Java or Alpine tag prevents a downgrade when upstream metadata is stale.

The annotated Git tag `java/JAVA-alpineALPINE` contains a JSON build manifest with the source commit, both archive URLs and SHA-256 checksums, and the exact Alpine version and multi-platform index digest.
New tags are never force-pushed or rewritten.
An upstream archive or Alpine digest respin with the same public versions gets a deterministic `-r<12-hex-fingerprint>` suffix instead of replacing the original managed release.
Existing completed, unmanaged exact-version indexes are left untouched because their original inputs cannot be recovered safely.
Git tags and Docker Hub, not a cache, are the source of truth.
Already-pinned incomplete releases are retried even if newer upstream versions have appeared; this repairs an existing release, not a new historical backfill.
A managed release is complete only when its multi-platform tag and both architecture tags are present.

Build, test and discover locally from the repository root:

[source,sh]
----
mvn -f _internal/pom.xml verify
java -jar _internal/target/java-updater.jar update --update-dry-run true
----

Dry-run is the default and writes only `_internal/target/plan.json`; it does not create or push tags or publish images.
The plan includes pinned manifests, a GitHub Actions matrix, and the number of remaining releases beyond the default batch limit of ten.
Use `--update-limit 20` to change the batch size, `--update-timeout PT2M` to override the HTTP timeout, or `--update-output /tmp/java-plan.json` to change the output location.

After reviewing the plan, apply from a clean, committed checkout with all remote tags fetched, a configured Git author, and permission to push new tags to `origin`:

[source,sh]
----
git fetch origin --tags
java -jar _internal/target/java-updater.jar update --update-dry-run false
----

Apply pins HEAD, creates annotated tags, and pushes them without force.
It does not itself build or publish Docker images.
For local tag creation outside the scheduled workflow, rerun the manual Java update workflow with dry-run disabled to publish the pending managed tags.
Do not apply an uncommitted implementation: release checkouts must contain the CLI, Dockerfile and smoke runner at the pinned commit.

The `Java update` workflow runs every Wednesday at 05:23 UTC and supports manual dispatch on `main`, defaulting to dry-run.
Pull requests run the offline Maven tests and build the minisite without publishing privileges.
Java image changes also run the separate `Java image verification` workflow: native AMD64 and ARM64 builds with fixed Alpine/JRE fixtures, followed by smoke and negative regression tests, without registry login or pushing images.
Its fixture pins are maintained in `.github/workflows/java-verify.yml` and do not affect production discovery.
External Actions are commit-pinned; `.github/dependabot.yml` proposes weekly action and internal Maven updates for review.
Review the first manual dry-run's `java-update-plan` artifact before enabling apply.
Scheduled runs apply automatically once this workflow is on the default branch; disable its schedule until the first reviewed rollout if necessary.
Apply needs `contents: write` for `GITHUB_TOKEN` and existing `DOCKERHUB_USERNAME` and `DOCKERHUB_TOKEN` secrets with push access to `ossyupiik/java`.
Repository rules must allow the workflow bot to create `java/*` tags.
The repository gate is `yupiik/dockerhub-java`; forks must intentionally change it to run publication.
The updater directly invokes the reusable `Java release` workflow because tags pushed with `GITHUB_TOKEN` do not trigger another workflow.
The legacy generic DockerHub workflow explicitly excludes Java refs; `java-docker` retains its separate workflow.

Each release builds on native AMD64 and ARM64 runners using the same `java/Dockerfile`, with explicit `ALPINE_IMAGE`, `DISTRIBUTION_URL` and `DISTRIBUTION_SHA256` build arguments.
There are no floating build defaults or separate ARM64 Dockerfile.
The archive is checksum-verified before extraction, and only the JRE is copied from the download stage.
The smoke runner checks the default command, exact Java release, Azul vendor, native JVM architecture, exact Alpine release and absence of `javac` before pushing the tested image.
The tags are `JAVA-alpineALPINE-amd64`, `JAVA-alpineALPINE-arm64` and `JAVA-alpineALPINE` for the merged multi-platform index.
No floating Java-major or Alpine-major aliases are moved.
The merge uses immutable per-architecture digests and verifies the resulting Linux AMD64/ARM64 platform set.

On retry, an already-published architecture is pulled, checked against the pinned input labels and smoke-tested again rather than rebuilt and overwritten.
A missing architecture alias can also be recovered from its existing multi-platform index.
Authentication, registry and metadata errors fail closed instead of being interpreted as missing releases.
Rerun the failed workflow or dispatch Java update with dry-run disabled to reconcile incomplete publications; never delete or move the annotated release tag.
The Alpine image and JRE archives are pinned, but `apk` runtime packages resolve from Alpine's repositories at the first build, so this is not a bit-for-bit reproducible package snapshot.
Pin the published multi-platform digest in production.
Native ARM64 testing and registry merge verification run in CI and require the configured runners and credentials.


== Java with Docker CLI

`ossyupiik/java-docker` provides a Java 25 JRE and Docker CLI 29.9.2 at `/usr/bin/docker` for applications controlling an external Docker Engine.
The shared `java-docker/Dockerfile` selects one of two variants with `ARG VARIANT=alpine`: the default `alpine` uses the pinned official Eclipse Temurin Alpine runtime, while `zulu` uses pinned Debian bookworm-slim and a verified official Azul Zulu glibc JRE archive.
Both variants copy only the pinned static Docker client from the official Docker CLI image and support `linux/amd64` and `linux/arm64` under each published image reference.
There is one build directory and one workflow for both variants, not a separate Zulu directory or workflow.

The image is runtime-only: it contains no Maven, gh, command-line or in-process Java compiler, Docker plugins or Docker daemon.
Both variants default to UID/GID `10001:10001`, `HOME=/tmp`, no entrypoint and `java --version` as their command.
They support a read-only root filesystem with writable `/tmp`, without root initialization or baked-in credentials.
The upstream system and Java CA stores are retained; custom trust must be provisioned explicitly rather than relying on Temurin's root-oriented certificate entrypoint.
The Zulu variant preserves the upstream JRE modules, legal notices and CDS archives, installs only the required Debian runtime libraries and system CA store without recommended packages, and keeps download tooling in a separate build stage.
Jib can use either variant as its base and generate the application's Java entrypoint without adding a Docker binary during the Maven build.

WARNING: Access to a Docker Engine socket grants host-administration capabilities even when the client runs as non-root.
Provision socket or remote-engine access explicitly on a dedicated trusted host; these images do not start a daemon or grant socket permissions.

The Temurin, Debian and Docker multi-platform image inputs are pinned by digest in `java-docker/Dockerfile`.
Both architecture-specific Zulu archives are verified against pinned official SHA-256 values, and Debian package resolution uses a fixed signed snapshot.
The fixed snapshot preserves package reproducibility; later security fixes require a reviewed snapshot update, rebuild and new release.
Updating either variant requires reviewing its affected pins, release version and smoke-test version checks, then rerunning native AMD64 and ARM64 tests.

Build and test locally with a host JDK 25 and a local Linux Docker daemon.
The default Alpine build does not require a variant argument:

[source,sh]
----
docker buildx build --load --platform linux/amd64 -t java-docker:alpine-local java-docker
java java-docker/test/SmokeTest.java java-docker:alpine-local amd64 alpine
----

Select the Zulu variant explicitly:

[source,sh]
----
docker buildx build --build-arg VARIANT=zulu --load --platform linux/amd64 -t java-docker:zulu-local java-docker
java java-docker/test/SmokeTest.java java-docker:zulu-local amd64 zulu
----

On a native ARM64 host, select `linux/arm64` and pass `arm64` to the smoke runner.
The shared runner accepts `java java-docker/test/SmokeTest.java IMAGE amd64 alpine|zulu`, with `alpine` as the default when the variant argument is omitted.
The old `java-docker/test/smoke.sh` remains a thin alias for the Java runner.
Set `SMOKE_HTTPS_URL=https://example.com` when invoking the runner to enable the optional Java TLS trust probe, which requires network access.

Both variants are checked for metadata, Java vendor/version, Java and static Docker execution, CA trust, absence of compilers and daemon executables, and the non-root/read-only contract with all capabilities dropped and no-new-privileges enabled.
Smoke tests never mount a Docker socket.
`SecureDirectoryStream` tests are mandatory only for Zulu, on both tmpfs and a writable bind mount, including descriptor-relative reads after directory replacement and rejection of file and directory symlinks.
An unsupported filesystem or runtime fails these Zulu checks rather than silently falling back to ordinary directory streams.
The Alpine variant is not compatible with a strict broker requiring `SecureDirectoryStream`.
Neither glibc nor the Java vendor alone guarantees secure directory handles on every filesystem provider; test the deployment's actual filesystem too.
These checks do not replace testing against the deployment's Docker Engine or a supply-chain/security review.

The single `java-docker.yml` workflow tests both variants on native AMD64 and ARM64 Ubuntu 26.04 runners, forming a two-variant by two-architecture matrix for pull requests and changes on `main`.
Releases use the unified tag prefix `java-docker/<full-image-version>`.
The workflow derives the image version directly from the Git tag, selecting `alpine` for `JAVA-alpineMAJOR.MINOR-dockerDOCKER_VERSION` or `zulu` for `JAVA-zulu-debianMAJOR-dockerDOCKER_VERSION`.
There is no release-version file or allowlist; malformed tag names are rejected.
The full Zulu Java version includes Azul's PSU suffix so the tag identifies the actual runtime.
For example, `java-docker/25.0.5-alpine3.24-docker29.9.2` maps to `ossyupiik/java-docker:25.0.5-alpine3.24-docker29.9.2`, and `java-docker/25.0.5.0.3-zulu-debian12-docker29.9.2` maps to `ossyupiik/java-docker:25.0.5.0.3-zulu-debian12-docker29.9.2`.
The Zulu variant is published only after merge through its release-tag workflow.
Publishing requires a release commit merged into `main`, successful native smoke tests and the existing Docker Hub secrets and repository write permissions.
A pull request, push to `main` or manual workflow invocation never publishes an image.
Pin the published multi-platform index digest in production to preserve platform selection and reproducibility.
The other Java images and their release workflow are unchanged.

A docker image using Yupiik Java docker (v17 as of today) and bootstraping H2 server.
It enables to use it as a remote database quite easily and makes development smoother in several cases - in particular in self-hosted kubernetes environments.

https://hub.docker.com/r/ossyupiik/h2/tags

Example usage:

[source,sh]
----
$ docker run yupiik/h2:2.1.214 -tcp -tcpAllowOthers -tcpPort 9092 -tcpPassword secret -baseDir /opt/storage/h2 [-ifNotExists]
----

Then you can connect to `jdbc:h2:tcp://172.17.0.2:2000/<database>` from any h2 client.
